# 性能优化改动清单

> 生成日期：2026-08-09
> 来源：对前端（Vue 3 + TypeScript）与后端（Rust + Tauri 2）热路径的全量性能审查
> 核心结论：虚拟滚动只解决了「DOM 行数」一层，当前主要瓶颈在 **消息 IPC 通路、YAML 全量落盘、脚本引擎重复编译** 三处，另有一处确定的内存泄漏和一处会导致大 payload 直接断连的配置缺陷。

## 优先级说明

| 级别 | 含义 |
|------|------|
| P0 | 高频场景下的主要瓶颈或功能级缺陷，优先修复 |
| P1 | 明显性能损耗，紧随 P0 之后 |
| P2 | 值得修但影响较小 / 纯清理项 |

## 一、消息 IPC 通路（Rust → 前端）

### 1.1 [P0] Rust 侧聚合 emit，payload 改 base64

- **位置**：`src-tauri/src/mqtt/client.rs:143-153`
- **问题**：
  - 每条 MQTT 消息单独 `app_handle.emit("mqtt-message", msg)`，每次 emit 都要经过 serde_json 序列化 → `format!` 拼 JS 脚本 → 主线程派发 → WebView2 跨进程 marshal（UTF-16）→ JS 引擎解析。
  - `payload: Vec<u8>` 被序列化为 JSON 数字数组（`[104,101,...]`），约 4 倍体积膨胀；前端 `JSON.parse` 后产生百万级装箱 number，GC 压力极大。
  - 一条 100 字节消息从 rumqttc 到 JS 约经过 7 次内存复制，峰值膨胀 15 倍以上。
  - 前端已有的 50ms 批处理（`src/stores/mqtt.ts:135-167`）发生在 IPC **之后**，救不了这一段。
- **改动**：
  1. eventloop 中攒批：累积 N 条（如 50 条）或 M 毫秒（如 30-50ms）后一次 emit 一个 `Vec<ReceivedMessage>`。
  2. payload 从 `Vec<u8>` 改为 base64 字符串（膨胀仅 1.33x），前端用原生解码还原为 `Uint8Array`。
  3. 前端 `src/stores/mqtt.ts:189` 的事件监听同步改为处理批量数组。
- **预期收益**：高频消息场景（1000 msg/s）的 CPU / 内存带宽占用下降一个数量级，这是全项目收益最大的单项改动。

### 1.2 [P0] 设置 rumqttc 包大小上限（功能级缺陷）

- **位置**：`src-tauri/src/mqtt/client.rs:61-84`
- **问题**：未配置 `max_incoming_packet_size` / `max_outgoing_packet_size`，rumqttc 0.24 默认仅 **10KB**。payload 超过 10KB 时 `eventloop.poll()` 报错 → 走 `client.rs:160` 的 `Err` 分支 → `break`，**连接直接断掉且不重连**。
- **改动**：`MqttOptions` 上显式调用 `set_max_packet_size(incoming, outgoing)`，给一个合理上限（如 10MB）。
- **预期收益**：大 payload 场景从「直接断连」变为可用。

### 1.3 [P0] 错误分支不应一律 break（无自动重连）

- **位置**：`src-tauri/src/mqtt/client.rs:160-177`
- **问题**:任何 `poll()` 错误（网络抖动、单个超大包）都 `break` 永久终止事件循环。rumqttc 的 `EventLoop::poll` 设计上可以继续轮询（内部会自动重连）。
- **改动**：区分错误类型——瞬时错误记录日志后 `continue`（可加退避），仅致命错误（认证失败等）才退出并通知前端。
- **预期收益**：客户端在高负载 / 弱网下不再一碰就断。

### 1.4 [P1] payload 大小上限与前端队列背压

- **位置**：`src-tauri/src/mqtt/client.rs:147`、`src/stores/mqtt.ts:64-66, 160-167`
- **问题**：
  - 后端整包原样进内存、进 IPC、进渲染，一条 10MB retained 消息可冻结 UI 数秒。
  - 前端 `messageQueue` 无上限，窗口最小化时 `setTimeout` 被浏览器节流，队列无界增长（1000 msg/s 后台 1 分钟 = 6 万条完整消息堆积）。
- **改动**：
  1. Rust 侧对超大 payload 截断（如保留前 64KB），消息对象记录 `original_length` 与 `truncated` 标记，前端展示提示。
  2. 前端队列长度超过阈值（如 2000）时立即同步 flush 并丢弃超限部分。
- **预期收益**：消除极端消息导致的 UI 冻结与后台 OOM 风险。

### 1.5 [P2] 消息热路径上的小拷贝

- **位置**：`src-tauri/src/mqtt/client.rs:146-150`
- **问题**：`publish.topic.clone()` 可直接 move；`payload.to_vec()` 对 `bytes::Bytes` 做完整 memcpy；每条消息 `chrono::Utc::now().to_rfc3339()` 分配字符串（25+ 字符），换 `u64` 毫秒时间戳只要 8 字节。
- **改动**：move 代替 clone；时间戳改数值型（前端格式化）。
- **预期收益**：热路径每条消息少 2-3 次分配，配合 1.1 一起改。

## 二、YAML 存储与阻塞 IO

### 2.1 [P0] 消息历史移出 YAML / save() 防抖

- **位置**：`src-tauri/src/db/mod.rs:98-102`（`save()`）、`db/mod.rs:221-252`（`create_message`）
- **问题**：任何数据改动（发一条消息、点一次模板计数）都全量序列化整个 data.yaml 并重写磁盘。3 个 server 存满消息（各 1000 条 × 1KB）时约 3MB，单次 save 阻塞 50-100ms。定时发布 100ms 间隔时磁盘被永久打满。
- **改动**（按收益排序，可组合）：
  1. **消息历史不再写入 data.yaml**：前端本来只展示内存中最新 1000 条；若需持久化，改为独立的 append-only JSONL 文件。
  2. `save()` 改为脏标记 + 后台防抖任务（每 1-2 秒最多落盘一次）。
  3. `create_message` 中的全表扫描计数与 `retain` 裁剪（`db/mod.rs:231-246`）改为按 server 分桶的 `VecDeque`，O(1) 裁剪。
- **预期收益**：消除「每条消息 = 一次 3MB 序列化 + 3MB 磁盘写」的最大 IO 瓶颈。

### 2.2 [P0] 原子写，防止数据损坏后被静默清空

- **位置**：`src-tauri/src/db/mod.rs:101`（`fs::write`）、`db/mod.rs:82`（`unwrap_or_default()`）
- **问题**：`fs::write` 先截断再写，崩溃 / 断电会留下半截 YAML；启动时解析失败走 `unwrap_or_default()`，**静默丢弃全部用户数据**。写入频率越高（见 2.1）触发概率越大。
- **改动**：写临时文件 + `rename` 原子替换；解析失败时保留损坏文件备份并提示，而非默认空数据。
- **预期收益**：数据安全性问题根除（严格说是正确性问题，但由高写入频率放大）。

### 2.3 [P0] 阻塞 IO 移出 tokio worker / 主线程

- **位置**：
  - async 命令内同步写盘：`src-tauri/src/commands/publish.rs:45`、`server.rs:11-23`、`template.rs:6-34`、`subscription.rs:25,77`
  - 同步命令跑在主线程：`commands/script.rs`、`env.rs`、`log.rs` 全部
  - `commands/settings.rs:63-70`：`blocking_pick_folder()` 在 async fn 内
- **问题**：async 命令中的同步落盘占死 tokio worker——MQTT eventloop 跑在同一 runtime 上，**用户点一下「保存模板」，消息流就顿一下**；同步命令则直接在主线程做 3MB 序列化 + 写盘，冻结 UI；文件夹选择对话框开多久 worker 就堵多久。
- **改动**：所有落盘统一走 `tauri::async_runtime::spawn_blocking`（或 2.1 的后台写入任务）；`pick_folder` 改非阻塞回调式或 `spawn_blocking`。
- **预期收益**：保存操作不再卡消息流、不再冻结 UI。

### 2.4 [P1] 读命令避免全量深拷贝

- **位置**：`src-tauri/src/db/mod.rs:107, 152-158, 262-268, 369-375, 455-462`
- **问题**：`get_servers` 连 `ca_cert` / `client_cert` / `client_key` PEM 字符串一起 clone；`get_templates` / `get_scripts` 拷贝所有 payload / code。UI 多处高频调用。
- **改动**：在锁 guard 上直接序列化返回，或返回不含大字段的精简 DTO。
- **预期收益**：减少每次 UI 刷新几十 KB 的无谓拷贝。

### 2.5 [P1] 修复消息分页（功能缺陷）

- **位置**：`src/stores/message.ts:21`（前端传 `offset`）、`src-tauri/src/commands/publish.rs:49-54`（命令签名无此参数）
- **问题**：serde 静默忽略未知参数，分页实际不生效，前端每次都从最新处重取。
- **改动**：命令签名补上 `offset` 参数并在 `get_messages` 中实现。

## 三、前端热路径

### 3.1 [P0] 脚本引擎编译缓存（投入产出比最高的单点修复）

- **位置**：`src/utils/scriptEngine.ts:685-689`（`new AsyncFunction`）、`:614-669`（sandbox 重建）、`:489-508`（crc32 查找表）
- **问题**：
  - 每条消息都重新拼接 `wrappedCode` 并 `new AsyncFunction(...)` 走完整解析 + 编译，1000 msg/s 配一个脚本 = 每秒 100-500ms 纯编译时间。
  - sandbox 对象每次执行重建，含 22 次 `.bind()` 分配。
  - `crc32` 每次调用重建 256 项查找表；`bytesToBase64`（`:26`）用 `String.fromCharCode(...bytes)` 展开，payload > 64KB 时抛 `RangeError`。
- **改动**：
  1. `Map<scriptCode, compiledFn>` 缓存编译产物，脚本内容变化 / `clearScriptCache` 时失效。
  2. `crypto` 对象与静态全局（JSON/Math/Date 等）提升为模块级常量，仅 `payload` / `topic` / `env` 每次传入。
  3. CRC 表提为模块级常量；`bytesToBase64` 改分块处理。
- **预期收益**：配脚本时 CPU 占用直接降一个数量级。

### 3.2 [P0] 消息派生数据入队时计算一次并缓存

- **位置**：
  - 过滤链：`src/components/mqtt/MessageList.vue:237-261`（`filteredMessages`）、`:278-293`（decode / hex）
  - 每行重复调用：`MessageList.vue:71-92`（`getTopicColor` × 3、`getMessageFormat` × 2）、`:296-346`（格式检测）
  - 重复实现：`src/components/mqtt/MessagePayload.vue:50-117`（与 MessageList 的格式检测各做一遍）
  - 时间格式化：`MessageList.vue:371-383`（每次隐式新建 `Intl.DateTimeFormat`）
- **问题**：搜索时每 50ms 对全部 1000 条消息即算即弃地做 `TextDecoder` + hex 化（3 倍长度字符串），1KB payload 下约 80MB/s 临时字符串垃圾，UI 锁死；滚动 / flush 时每可见行重复做通配符匹配、`JSON.parse`、全字节扫描。
- **改动**：
  1. 消息入队时（batch flush 处）一次性计算并挂到消息对象上：`decodedText`、`hexText`（可惰性 getter + memo）、`payloadFormat`、`formattedTime`。
  2. `getTopicColor` 建 `topic → color` 的 Map 缓存（订阅变化时失效）。
  3. `Intl.DateTimeFormat` 提为模块级复用实例。
  4. 两个组件的格式检测统一读消息对象上的缓存字段，删除运行时检测。
- **预期收益**：搜索从「锁死」变流畅；滚动帧率明显提升。

### 3.3 [P0] 预览截断 payload

- **位置**：`src/components/mqtt/MessagePayload.vue:120-131`
- **问题**：预览模式明确不截断，一行 50KB JSON = 大量文本节点 + `white-space: pre-wrap; word-break: break-all`（最贵的文本布局模式），单帧 layout 数百毫秒，基本抵消虚拟滚动收益；二进制还要先生成 3 倍长度 hex 字符串。行高失控也导致 `min-item-size=70`（`MessageList.vue:45`）估算严重失真。
- **改动**：预览截断至 200-500 字符（hex 截断至 64 字节）+ 省略号提示；完整内容仍在详情弹窗查看。
- **预期收益**：大 payload 场景从「冻结」变可用，行高趋于固定后滚动条不再跳变。

### 3.4 [P0] 修复虚拟滚动 sizes 内存泄漏

- **位置**：`src/stores/mqtt.ts:43`（全局递增 id）× vue-virtual-scroller 内部 `sizes` 缓存
- **问题**：库按 item id 存行高且从不按 key 删除；消息 id 全局单调递增，被裁掉的旧 id 的 size 记录永久留存。1000 msg/s 跑 1 小时累积 360 万个 reactive 键，**跑一夜必 OOM**。
- **改动**（三选一）：
  1. 裁剪消息时定期调用 scroller 的 `forceUpdate()` 重置 sizes；
  2. 3.3 落地后行高固定，改用 `RecycleScroller`（固定行高，无 sizes 缓存问题）；
  3. 让 id 在有界取值域内复用。
- **预期收益**：消除长时间运行的内存持续上涨与 OOM。

### 3.5 [P1] 缓存击穿：脚本 / 环境变量缓存加 in-flight 去重

- **位置**：`src/stores/mqtt.ts:69-88`（`getCachedScripts`）、`:101-120`（`getCachedEnvVariables`）
- **问题**：缓存写回发生在 `await invoke` 之后，TTL（5s）到期瞬间并发到达的所有消息各自发起一次 IPC + DB 全量 clone，每 5 秒一次「惊群」，周期性卡顿 200ms+。
- **改动**：缓存存 `Promise<T>` 而非结果，miss 时先把 pending Promise 写入 Map。
- **附带**：`PublishPanel.vue:249` 与 `ScheduledPublishDialog.vue:451` 每次发布 / 每条定时消息都直接 `invoke("get_enabled_scripts")`，应统一复用该缓存。

### 3.6 [P1] 错误处理加聚合节流（坏脚本 ≠ 应用崩溃）

- **位置**：`src/utils/errorHandler.ts:52-67, 100-102, 129-142`、`src/stores/mqtt.ts:212`、`src-tauri/src/log/mod.rs:49-88`
- **问题**：接收路径上脚本每报一次错就 `console.error(完整 stack)` + `invoke('write_error_log')`；Rust 侧每写一行日志做 1 次 stat + 1 次 open + 1 次 write + 全目录 `read_dir`（每行都触发 `cleanup_old_logs`），且是主线程同步命令。1000 msg/s 流上一个有 bug 的脚本几秒内让应用完全无响应。
- **改动**：
  1. 前端：同一 `type + message` 时间窗口内去重计数（「该错误已发生 N 次」），文件写入批量化（500ms 或 100 条一批）。
  2. Rust：日志文件句柄持久化 + `BufWriter`；`cleanup_old_logs` 改按次数 / 时间采样触发；命令移出主线程。
- **预期收益**：消除「用户脚本有 bug = 应用卡死」的悬崖。

### 3.7 [P1] 消息接收路径保序 + 同步快路径

- **位置**：`src/stores/mqtt.ts:189-215`
- **问题**：事件回调是 async，配了脚本时慢脚本消息会被快脚本消息超车，**列表乱序**（对调试工具是功能缺陷）；未配脚本时每条消息也要白付 microtask 开销。
- **改动**：先同步 `queueMessage` 保证顺序，脚本处理结果异步回填；或用同步 `hasScripts` 标志走纯同步快路径。

### 3.8 [P1] flush 减少数组拷贝

- **位置**：`src/stores/mqtt.ts:135-151`
- **问题**：每 50ms 拷 Map + `[...new, ...existing]` 展开 + `slice(0, 1000)`，约 4 万次元素拷贝 / 秒；数组身份变化还级联触发虚拟滚动库内部三处 O(N) 遍历（其中一处 `flush: 'sync'` watch 每次 `.slice()` 整个数组）。
- **改动**：改环形缓冲或就地增删 + `triggerRef` 手动通知；消息上限 1000 提供 UI 配置项（低速调试时可调大、高速时可调小）。

## 四、构建与连接层

### 4.1 [P0] Cargo.toml 添加 release profile（改一次就完，白送性能）

- **位置**：`src-tauri/Cargo.toml`（当前无 `[profile.release]`）
- **改动**：

```toml
[profile.release]
lto = "thin"          # 或 "fat"
codegen-units = 1
strip = true
panic = "abort"
```

- **预期收益**：热路径全是 serde 泛型单态化代码，LTO + cgu=1 对序列化吞吐通常有 10-25% 提升；strip 可减 30-50% 二进制体积。

### 4.2 [P1] 缓存系统根证书库

- **位置**：`src-tauri/src/mqtt/client.rs:298`
- **问题**：每次 TLS 连接都 `load_native_certs()`，Windows 上读注册表解析 150-400 张证书，50-200ms，且跑在 async fn 里占 tokio worker；断线重连每次重付。
- **改动**：`OnceLock<RootCertStore>` 缓存首次加载结果。

### 4.3 [P1] 修复重连竞态

- **位置**：`src-tauri/src/mqtt/client.rs:51, 92, 185-186`
- **问题**：`connect` 开头 `disconnect` 只发信号不等旧任务退出；旧任务退出时无条件 `clients.remove(&server_id)`，可能删掉**新**连接的句柄——表现为「显示未连接但底层还在收消息」，旧 eventloop 泄漏。
- **改动**：加 generation counter（或句柄比对），remove 前校验是同一代连接。
